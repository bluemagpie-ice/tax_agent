# Research 第二阶段第一轮

## 基线与根因

第一阶段真实矩阵使用工作区源码，记录所在的 Git HEAD 为 `91d5692ddfce59b9dfa83ed15e4e428cf9a29b24`。本轮开工时，案例数据、Research Agent、解析器、本地检索工具和向量实现的 SHA-256 与第一阶段 manifest 一致。矩阵运行器的哈希不同，第一阶段已在实测结束后补了进度快照和参考复核队列。基线文件原地保留。

- **证据评估截断。** 8 个终态为结构化失败的案例，16 次评估请求均明确返回 `finish_reason=length`。首次上限为 1,536，修复为 2,730。旧流程给多个子问题重复输出原文摘录和所属期摘录，并启用 DeepSeek 推理模式。成功的旧评估样本单次记录了 658、704 或 1,883 个推理 token。失败请求未导出用量，无法拆分其中的正文与推理占比。另一次 4,096 token 诊断为 `OpenAITimeoutError`，与截断分别统计。
- **事实提取格式。** 二手房旧响应把字段值包在 `properties` 中，`facts`、`unknowns`、`tax_types` 的实际字符串列表位于 `items`，同时带有 `type`、`title`、`maxItems` 等声明。完整原响应的 4 次只读回放均通过新解析器，其中 3 次触发确定性修复。只有无歧义的字符串数组包装会展开，数组类型和数量仍由 Pydantic 校验。事实仍须能定位到用户原话，补充事实仍使用增量节点处理。
- **超时。** 基线 4 条硬超时落在检索 2 次、评估 1 次、补检 1 次。基线已保存阶段中，理解平均 2.24 秒、最长 2.75 秒，规划 8.79 / 21.54 秒，检索 3.80 / 13.01 秒，评估 11.24 / 29.83 秒，补检 10.53 / 24.01 秒。统计按可恢复的阶段记录计算，硬超时未完成节点没有完整耗时。
- **工具预算。** 3 个耗尽均来自 C 组，每次恰好 12 调用。每题有 6–7 次空本地检索、2 次官网搜索、3 次原文读取，两道历史题另有一次案例召回。旧补检会重新调用模型规划，再从新计划启动多步检索。现有精确缓存可复用成功查询，但同一术语的 Unicode 或空白差异、链接片段差异曾使缓存分裂。

## 改动

1. `ResearchAgent.assess` 及 `assessment_evidence` 使用有上限的原文段落编号。一次评估覆盖最多四个待核查子问题，程序校验段落编号、实际送入模型的证据、原文匹配、来源和所属期。已经充分覆盖的题目保留可追溯关联。评估仅输出段落 ID、判断、缺口和有限的新关键词。报告提示保留相关原文，省去覆盖表中重复的摘录。正式初稿仍执行逐题引用及合规校验。
2. `ResearchAgent.ask` 对当前 DeepSeek 端点使用其 JSON Object 模式，评估及规划禁用思考模式并提供小型实例。评估输出上限从 1,536 调为 1,024，截断只允许一次有界修复。HTTP 模型超时和案例、工具预算沿用基线。新增字段只记录状态、请求模式、输入证据数量、可获取的 token 用量和格式修复字段名。JSON Object 控制输出格式，字段契约继续由本地解析器执行。 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/) · [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)
3. `parse_output` 仅展开已知事实字段的无损数组包装。格式修复和模型重试分别记录。遇到定义式 `items`、混合类型、超长数组或存在歧义的值，继续严格拒绝。
4. `ResearchAgent.retrieve` 合并规范化后相同的查询和仅片段不同的 URL，保留所有子问题关联。`supplement` 使用评估返回的最多两条新关键词，省去一次完整模型规划。没有新增证据、没有新查询或所有题均充分时结束补检。
5. `reference_analysis` 通过创建请求显式开启，页面提供对应选项。证据缺口可产出带待核实项的参考分析，单独保存状态和内容。该状态没有报告版本和定稿入口。模型或工具技术失败和调用预算耗尽仍有独立失败码。正式证据须来自已读取的官方来源或带有可追溯文件 ID 的系统政策，并通过原文、期间和引用检查。

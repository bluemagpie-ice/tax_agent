## 原任务 06c4c278

以只读方式打开业务 SQLite 和 LangGraph 检查点，找到完整任务 ID `06c4c278696b4e80b531279a533351d0`、19 个检查点和一版报告。历史任务停在 `awaiting_review`，版本 1 是旧代码生成的失败占位报告。原任务及历史报告保持原样。

检查点保留了当时的模型响应、研究计划、检索参数、返回内容、初稿及耗时。研究累计执行约 121 秒，等待用户补充事实的时间另计。补充事实后，两轮检索分别约 26 秒和 23 秒，证据评估约 14 秒，初稿生成约 26 秒。历史记录没有首个 SSE 数据到达浏览器的时刻，也没有保存当时 Bing、模型列表接口的原始 HTTP 状态与代理错误。

实际调用包含 1 次案例检索、8 次本地政策检索和 7 次官网定向检索。官网结果全部为空，9 条候选摘录均来自本地政策知识库，向量分数约在 0.54 至 0.72 之间。根据运行代码推断，当时查的是共享 `tax_chunks`，在任务所属租户权限内走语义检索，没有指定单独知识库 ID。部分检索词用了宽泛的跨地区建筑服务、免税、预征和申报概念，结果中出现了代扣代缴、行政处罚等低相关主题。

第一次证据核查保存了四项缺口，分别涉及是否应在项目地预缴、门槛判定、计算和地点时限、机构所在地申报抵减。后一次核查遇到工具预算耗尽，旧节点用空列表覆盖了这些缺口。原任务的 0/4 没有对应四项已支持的结论，9 条是候选资料数量。

原模型初稿的 JSON 可正常解析。用当时的实际候选资料重放校验，可复现 `财税〔2016〕36号` 缺少可见依据。历史七次成功模型调用的供应商用量合计 13,868 token，当时本地保守预算累计 85,457，修正请求因预算上限在发送前被拦下。旧修正分支又将失败文案填入研究范围和答复草稿，最终留下了可进入复核的占位版本。

## 如何复验

1. 在项目目录打开 PowerShell，运行 `.\.venv\Scripts\python.exe -m uvicorn web.main:app --host 127.0.0.1 --port 8000`。浏览器访问 `http://127.0.0.1:8000`。
2. 在设置中检查当前供应商、模型、API 地址。点击 **检测连接**，看到模型响应才表示连接成功。若填写了新 Key，使用同一个配置点击保存，再运行研究。
3. 进入 **Research 研究**，新建任务，写明 2026 年第一季度和全部模拟事实，勾选 **检索并读取官方网页**。点击 **创建并开始研究** 后，观察任务号和真实阶段。
4. 如果出现追问，补充可确认的业务事实，或点 **保留未知并继续**。打开 **检索与证据覆盖详情** 查看哪些子问题有原文支持。
5. 有待复核草稿时，展开核心依据，点 **查看来源** 核对条文和日期。失败时查看缺口或未匹配引用。刷新浏览器后进入 Research，从下拉框选回同一任务，按页面状态继续。
6. 新建对照任务，只将 30 万改成 29 万。确认两次使用的政策依据和分析对应实际金额。先不贴链接可以验证自动检索。如果需要验证指定来源，再将两份公告链接粘贴在题目末尾。

开发者可从仓库根目录运行 `.\.venv\Scripts\python.exe -X utf8 -m scripts.recheck_research_live`，加 `--with-sources` 单独验证直接读取两份公告。该命令使用真实模型和公开搜索，只读查询政策库，临时 SQLite 在退出后清理。
